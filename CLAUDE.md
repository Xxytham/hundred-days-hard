# 100 Days Hard — notes for Claude

A gym tracker for a 100-day challenge, built for the owner and shared with friends. One HTML file (`app.html`) is the whole app. It ships three ways:

1. **Installed Android app (main one the owner uses).** `android/` wraps `app.html` in a WebView APK. Data lives on the phone. Samsung Health numbers arrive through Health Connect.
3. **iPhone home-screen web app** for friends, at https://xxytham.github.io/hundred-days-hard/ (GitHub Pages, built by `web/build.sh`). Data lives in that phone's browser storage. The friends' download page is `/get/`.
2. **Claude artifact (web).** https://claude.ai/artifact/XAhfUhWMsa4JCgrTkEJTEE, published from `app.html`. Data lives in the artifact's database under the owner's private `data/users/<id>/` path.

The owner is not a programmer and talks to you from a phone. Keep explanations plain, test before shipping, and say what you could not test.

## Ground rules

- **No personal data in code.** Friends install the same app, so defaults stay generic (no goals, generic tasks, start date = today). The owner's own goals and settings live in their saved data, not in `defaultGoals()`/`defaultSettings()`.
- **Never lose the owner's data.** Every change to the stored format needs a migration in `normalizeDay()` (or the matching loader), and old backups must still restore.
- **Never make a new signing key.** The APK is signed with the key in the `KEYSTORE_B64` Actions secret. A different key means the phone refuses the update unless the app is uninstalled, which wipes its data. `android/build.sh` refuses to sign without the real key; use `TEST=1` for local test builds.
- **Bump `android/VERSION` (`code` +1, `name`) for every APK release** and add a `## v<name> · Short description` section to `CHANGELOG.md` (the description, a few plain words, names the release and shows in the app's update banner; leave it off and the banner shows only the version). Pushing a VERSION change to `main` makes GitHub Actions build and publish the signed APK as a Release.
- After changing `app.html`, also republish the artifact (see below) so both versions stay the same.

## How the app works

Tabs: **Today**, **Stats**, **Progress**, **Goals**. Show less at once and let the user open things; avoid long stacks. Settings order: Goals, Daily tasks, Notifications & widget (APK only), Coach (APK, only where Gemini Nano can run), Challenge, Samsung Health, App updates, Share, Backup (the backup dot scrolls straight to Backup). Settings opens from the day counter in the top corner (`gaugeSVG()`: a 300° ring with the gear in the gap at the bottom). In setup, the big inline numbers (`.inline-num`) clear on focus and restore if left empty.

- **First-time setup:** shown while `settings.setupDone` is false (fresh installs only). Steps: welcome ("Welcome to [N] Days Hard", N is an editable number) or restore → "Today is day [n]" with the last day's date → targets → daily tasks (`TASK_PRESETS` plus custom) → Samsung Health (APK only) → done. The targets step picks a calorie goal (Lose fat or Build muscle) and has **Suggest for me** (Katch-McArdle when a body-fat range is picked, otherwise Mifflin-St Jeor; × activity 1.4/1.55/1.75; × 0.8 to lose or 1.1 to build; lose rounds to the nearest 100. Protein is 1 g per lb of lean mass, or 0.8 g per lb of body weight if body fat is unknown, capped at 250 g. The weight entered becomes today's weigh-in. `suggestCheck()` lists what's missing) and **I know my numbers**. Anyone with saved data from before v0.4 is marked `setupDone` on load.
- **Streak:** `streakInfo()` counts consecutive days with every daily task done. Today counts once it's complete; until then the streak runs through yesterday. It's shown on Today with the last 7 days, and the Progress tab uses the same number.
- **Backup dot:** next to the date. `backupState()` is green if `settings.lastExport` (last copy sent off the phone) is within 7 days, yellow within 14, and red otherwise or if there's never been one. It's always green in the Claude artifact once synced. Tapping it opens Settings.
- **Updates:** tapping Update calls `AndroidBridge.updateApp(APK_URL)`: the app downloads the APK into its cache (progress through `window.__updateState`, shown in the banner by `updateBannerInner()`), checks it's a newer version of this package, and installs it with a `PackageInstaller` session, so Android shows its own "Update this app?" prompt (`REQUEST_INSTALL_PACKAGES`; the first time, Android sends the user to allow installs from this app, and the update carries on when they come back). The APK checks `api.github.com/repos/Xxytham/hundred-days-hard/releases/latest` (uncached) on launch, every time the app resumes, and when Settings opens (at most once a minute). It shows an "Update" banner if the tag is newer than `AndroidBridge.appVersion()`, with the release's description (`updateAbout`, taken from a release name like `v0.9 · Workout button…`, which the workflow builds from the changelog heading). The web app updates itself (network-first page in `sw.js`, with the cache name bumped by version).
- **Sharing:** Settings has "Share with friends": the link `https://xxytham.github.io/hundred-days-hard/get/`, a QR code (qrcode-generator from cdnjs, loaded on demand), plus share/copy buttons. Releases and Pages only work for friends while the repo is **public**.

- **Challenge length:** `settings.totalDays` (default 100) drives the plate, the grid, "Day N of X" and the streak range. When the last day is done (or passed), Today shows a finish card with round stats. "Start another round" appends `{startDate, totalDays}` to `settings.rounds` and makes today day 1. History is never deleted.
- **Tasks that tick themselves:** `METRICS` covers `steps`, `sleep` and `workout` (task ids). The workout count is `workoutParts(day)`, using Samsung Health sessions of 10+ minutes. With a target of 1, a Push/Pull/Legs saved in the app or any cardio session counts. With a target of N ≥ 2 (the owner's rule), it takes one Push/Pull/Legs saved in the app plus N−1 cardio sessions. Walking sessions count as cardio only from 1 mile (`walkCounts`): `miles` comes from DistanceRecords inside the session, falling back to `steps` inside the session ÷ 2,000; a walk with neither doesn't count. Strength-type sessions (Other workout, strength training, weightlifting, calisthenics) never count; their minutes are only shown next to the saved workout. `workoutNames()` adds a "still need …" hint. Target is `settings.workoutsTarget` (default 1; the owner uses 2). Existing users got a one-time card to turn this on (`settings.workoutOffered`). Ticks the app made are recorded in `day.autoTicks` and come off if the value drops below the target; manual ticks clear that flag and stay. Names come from `settings.stepsTarget`/`sleepTarget`. Water used to be read too, but the owner found it unreliable, so it was dropped in v0.5.1; "Drink 3 L of water" is a manual task and old `day.health.waterL` values are ignored. Synced values live in `day.health` and tick the task when they reach the target (never unticking). People who set up before v0.5 get a one-time "Add them" card (`settings.autoOffered`).
- **Tasks count from `addedOn` until `removedOn`:** `tasksFor(date)` (`taskOn()`) counts a task only on days it existed. Adding one (`addTask()`, always with `addedOn`) never breaks past perfect days or a streak, and removing one (`removeTask()`) sets `removedOn` instead of deleting it (unless it was added that same day), so past days keep counting it. Adding a removed task back records the gap in `off: [[from, to]]`. Current lists use `activeTasks()`.
- **Targets apply from today on:** calorie goal and aim, protein, steps, sleep and workouts a day are changed only through `setTargets()`, which keeps `settings.targetLog` (a snapshot of the targets from each day they changed; `"0000-00-00"` = before the first change). `TG(date)` gives a day's targets (today and later = the settings). Anything about a particular day uses that day's targets: auto-ticks (`autoMetricHabits`, `autoProteinHabit`, also on every Samsung Health sync), the day shown on Today (food bars, the line under the coach, task names), and each bar in the Stats charts (`m.goal(date)`, `calStatus(v, date)`). `calAim/calRange/calStatus` take an optional date; `workoutParts/workoutNames/workoutsTarget` and `METRICS` take a targets object (`st`). The coach's look at this week, the goal lines and the widget use today's targets.
- **Stats tab (`renderStats()`):** a Connect card while any watch stat isn't shared (`WATCH_STATS`; "Not now" stores the missing list in `settings.watchOffer` and hides it until that list changes), then a row of section chips (`STAT_TABS`: Strength · Body · Heart · Sleep · Energy · Food; `statTab`; a section shows only once it has data). Strength is `strengthStats()` (`strengthTrend()`: each exercise's est. 1RM against its first session, averaged over all exercises and per day type, drawn with `lineChart()`). The other sections come from the `STATS` list: "line" stats (weight, body fat, BMR, resting HR, HRV, VO2 max, blood oxygen) show the latest reading and its change since day 1, green/red by the overall trend (a least-squares line through every reading, so one odd reading can't flip it; flat is neutral) times `better` (BMR: down is good when losing fat, up when building); "bar" stats (sleep, deep/REM/light sleep, calories eaten, protein, calories burned, eaten − burned, steps, workout minutes) show a 7-day average (or total, for `total`) and a `barChart(m, b)` from day 1 to today (`challengeDates()`) against the goal. Line stats and per-exercise charts also use every reading since day 1. One tile per section is open at a time (`statSel[section]`, first by default, "" when closed); its chart opens right under that tile's row of two. Resting HR uses Health Connect's resting HR if any app shares it, else `sleepHr` (average heart rate during the night's sleep, labeled "average while asleep"). Samsung Health doesn't share HRV, stress, skin temperature or running form.
- **Stats: Food** (`NUTRIENTS` → `nutrStat()`, from `day.health.nutr`): one bar tile per nutrient that has data, against generic adult recommended amounts (US National Academies, the higher one where men and women differ; iron 8 mg; fiber 14 g per 1,000 kcal of the calorie goal, at least 25 g). `max` nutrients are limits (sodium 2,300 mg, saturated fat 10% of the calorie goal, caffeine 400 mg): bars under the line are green, over it red. Nutrients without a goal (sugar, carbs, fat, trans fat, cholesterol) are neutral. Food stats are `past`: the 7-day average leaves out today and today's bar stays neutral, since the day's still being logged. Within 3% (`near`) counts as on target. A line on top gives where the week's calories came from (`macroSplit()`).
- **Stats: a coach note under each section** (`scoachHTML()`, after the section's panel; only where the Today coach is on and has said hello): `sectionFacts(sec, list)` takes the Today coach's own lines for that section (from `buildFacts()`, by their opening words), one line per stat (`statFact()`: trend direction and whether it's good for the aim or for health, the last 2 weeks, the week's average against the goal or limit, deep/REM as a share of sleep against typical ranges), and for Food what's on target, what needs more and what's over a limit. Its candidates (`secPicks`; Strength has one per exercise that's gone up and per new best this week) are picked the same way (`choosePicks()`), except that Food always nudges its top two. `scoachWrite()` asks for 2–3 sentences under 70 words about that section only (for Food: what's going well, then what they need more of, and it may name an everyday food rich in it). Notes are cached per section in localStorage (`hundred-days-hard.coachStats`) and rewritten, for the section on screen only, on a new day or when the facts changed and the note is 2+ hours old; one section writes at a time (`scoach.busy`, `scoach.next`). The ⋯ menu has Write a new note (`scoach-refresh`), Minimize and Turn off coach, which follow the same `settings.coach` as Today; tapping the note minimizes it. It uses its own typer (`makeTyper()`, also behind Today's `typer`) and the barbell loader with section captions (`CAPTIONS[sec]`).
- **Calories burned** (`burnedOf(d, date)`, Stats → Energy, and the coach's plateau check) is the whole day. Samsung Health shares only workout calories with Health Connect, so when `burned` is no more than the workouts' own calories (or less than a resting day), it's worked out: BMR (the watch's latest, else Katch-McArdle from weight and body fat, else about 10 × kg + 900; today only the share of the day so far) + workouts (`active`, else `burned` minus their resting share) + walking outside workouts (day steps minus steps inside sessions × kg × 0.0004). A real all-day total from another app is used, minus the cut below. Workout calories are cut because watches overestimate them (`WORKOUT_CUT`: cardio × 0.8, strength-type sessions incl. "Other workout" × 0.65; lab studies show roughly 15–25% over for steady cardio and worse accuracy for lifting). Walking outside workouts isn't cut. The chart footnote says when it's worked out (`burnFoot`).
- **Progress tab:** Strength tickers (Push/Pull/Legs toggle: `strType` starts on the last workout's type, and tapping the selected one again sets it to null and folds the list), each exercise under one tab only (`homeOf()`: its group's home, `GROUP_HOME`: chest/triceps/shoulders → Push, back/biceps/forearms/abs → Pull, legs → Legs; the group is the one it was logged in on a day of its own kind (pull-ups under Back on a pull day; plans count too), else what `guessAny()` says from its name, else wherever else it's been logged, else the first group of the day type it's done on most. So pull-ups done on a push day list under Pull, and abs only ever under Pull), grouped (`.tick-group` headings with the group's average change), then The N grid with perfect days, streak and average kcal inside it.
- **Goals tab:** one panel (`renderGoals()`; `newGoalOpen` shows the add form). Open things close in place: tapping an open exercise's row or chart, a body tile or its chart, or a goal's row closes it, and Back closes them too.
- **Apple Health:** not possible from the iPhone web app. It would need a native iOS app and an Apple developer account.
- **Day counter:** `settings.startDate` is day 1 of the current round.
- **Calorie goal:** `settings.calorieAim` is "lose" (default, including for anyone set up before v0.6) or "build". Lose = land within `calorieGoal` ± 100; build = reach at least `calorieGoal`. `calStatus(kcal)` drives Today's food bar, the coach's facts and the calorie chart. One line under the streak and coach (`coachLine()`) says the calories and protein still to go; it never mentions tasks.
- **Food:** one daily total for calories and protein (the owner logs food in Samsung Health). In the APK these fill in from Health Connect on open/resume. A value the owner types sets `kcalSrc: "manual"`, and synced data never overwrites it. The boxes are the bars (`foodBoxes()`/`foodFill()`): Calories full width and tall, Protein full width and slimmer underneath. The fill is a solid color clipped to `--p` (blue under, green met, red over; protein always green); "Lose fat" scales to 110% of the range top. The number is drawn twice (`.tot-num`): in ink, and in `--on-color` clipped to the same width as the fill, so it flips color where the bar passes under it. The real input sits on top with transparent text and a visible caret. While a box has focus the plain input shows, the fill dims and the bar doesn't move. When the day's totals change (typed and left, or synced), `animateFood()` (run after each Today redraw) counts from what's shown (`foodShown[date]`) to the new value over 700 ms, and `paintFood()` sets `--p`, `--b` (brightness: the fill mixes from `--fade-floor` up to full color as it nears the goal) and `--g` (calories blends blue → green over the last 30% to the goal) every frame. Opening the app or another day draws the bars at their values without animating.
- **Redraws while typing:** a `change` fires as you leave a box, before the next tapped box has focus, so handlers call `renderSoon()` (main page) or `drawWorkoutSoon()` (workout sheet) instead of redrawing on the spot. Otherwise the redraw swaps the next box out from under the tap.
- **Daily tasks:** checklist from `settings.habits`. `protein` auto-checks when the protein goal is met, and `workout` checks when a workout is saved.
- **Workout button:** Today has no Push / Pull / Legs tile. A red + (`#fab`, outside `main`, shown via `body.fab-on` on the Today tab only, hidden while the keyboard is open) opens a small menu (`fabMenu()`) with Push / Pull / Legs and when each was last done; if the day already has a workout, + opens it. The workout card on Today only appears once a workout exists.
- **Typing in the workout sheet:** `onViewport()` spots the keyboard (page or visual viewport at least 120 px shorter than its tallest at this width). While it's open, `body.kb` hides the +, `.sheet.typing` hides the sticky bottom buttons, and `fitTyping()` scrolls the sheet so the card being typed in sits just above the keyboard. Weight and reps boxes (`srow()`: one full-width row each, `type="text"` with a numeric keyboard) clear when tapped, showing the old number as the placeholder, and get it back if left empty. Enter/Next on a set's weight goes to its reps. Typing stores the number without redrawing (into the set named by the box's `data-k`), so a tap on a button straight after still lands.
- **Workouts (v0.20):** each day type has a plan, `settings.plans[type] = [{name, group, off?}]`. `planFor(type, without?)` = the stored plan minus `off` entries, plus every exercise from past saved sessions of that type (newest first; `mergeInto()` slots each one in right after the exercise done before it, so the logged order and groups hold, e.g. Dead hang under Forearms on a push day), plus anything else the Progress tab lists under that day type (`homeExercises()`, via `homeOf()`). `without` leaves one day's session out, used while saving it. So nothing ever drops off a plan by itself. **Never remove an exercise from a plan unless the user explicitly says so:** the only way off is Remove in "Reorder or remove" on the latest session of that type (`planOff()`, sets `off: true`, with Undo); adding it again puts it back. `setPlan()` keeps `off` entries. Starting a workout builds each exercise with `newEx()`: `e.last` = the sets from the last time it was done (`prevExercise()`: any day type; the newest before this day, or the newest after it when logging an earlier day), and `setList` = one placeholder `{w, r, done: false}` with set 1's numbers. A set without `done` (every saved workout, everything older) counts as done (`isDone`). `prepDraftEx()` (a function declaration, because `normalizeDay()` runs it for unsaved workouts while saved days load, before the rest of the script; `openWorkout()` runs it again) turns pre-v0.20 drafts, which kept last time's sets as planned rows, into this shape.
  - **Groups:** the sheet shows the groups for the type (`GROUPS`: push = chest/triceps/shoulders/abs, pull = back/biceps/forearms/abs, legs = "" (no heading) + abs), then one **Other** heading at the bottom (`OTHER`, `sheetGroups()`, `inGroup()`, `sheetLabel()`) for any exercise whose group isn't one of the day's own: pull-ups or a dead hang on a push day, push-ups on a pull day. Those keep their real group in the data, so Progress lists them under their own day. Other has no + Add; an exercise added under a day's heading that belongs elsewhere goes under Other with a toast. Dragging into Other keeps an exercise's own group (or, from one of the day's groups, takes the one its name says). There are never new groups. `othersOnce()` (flag `settings.othersSorted`, v0.24) moved, once, exercises sitting in one of their day's own groups although `guessAny()` says another day's group (pull-ups under Chest on a push day); abs never move. `groupFor()` = `knownGroup()` (this day's plan, else the last time it was done on any day, else another plan), else `guessGroup()` (`guessAny()` from the name across all groups, else the day's first group). Adding an exercise ignores the heading tapped when the exercise is known or its name says where it goes, with a toast. `regroupOnce()` (flag `settings.groupsSorted`) moved exercises that had landed in a day's first group only because nothing else fit.
  - **Logging (no "Log set" button):** nothing opens by itself. Tapping an exercise opens it and starts it (`startEx()`: the placeholder becomes set 1, done), because that's the one you're doing. Collapsed rows are one line (`exBlock`: dashed circle = not started, "usually 3 × 30×12"; green tick = started, "3 sets · best …"). The open one (`wOpen`, `.ex.open`: 2 px outline, lifted, spaced off its neighbours) shows "Last time: …" (`e.last`, or the previous session when reopening a saved workout), the sets done as tappable rows, and the current set (`curIdx`: the latest, or the one tapped) with big weight/reps steppers. While it's open, the sticky bottom has **+ Set N** (appends `nextSet()`: last time's matching set, moved by however much you changed the set before it; more sets than last time copy the one before) and **Done** (folds it up and scrolls its row into view, so you pick the next one). Otherwise the bottom is **Finish workout**. **Remove** on the current set deletes it; removing the only set un-starts the exercise (toast with Undo). **Try heavier** (`heavier()`): if the last two sessions before this day had the same top set (weight and reps), a pill offers one step up (5 lb / 2.5 kg, or +1 rep for bodyweight). Tapping it sets `e.bump`, applied to today's sets at that weight and to `lastPlan()`, which `nextSet()` uses. There's no Swap (removed in v0.18.2), and no `<datalist>` name suggestions: the WebView draws datalist options over the page.
  - **Adding:** each group heading has **+ Add** (name only; known exercises load their last sets, new ones start at 0 × 10 with the weight box focused). The added exercise opens and is started. A brand-new exercise is sorted once by the coach (`aiSortExercise()`: asks Gemini Nano for one group word, the day's own groups first and the others only if it clearly belongs elsewhere, matched with `AI_GROUP`; moves it only if you haven't moved it since, with a toast and Undo; skipped when the coach is off or unavailable).
  - **Finish workout** saves only started exercises with their sets, and strips `done`, `last` and `bump`. It never asks anything (the old "Keep for next time / Just today" question was removed in v0.23.5, after a Back on it seemed to lose the owner's push day). On the latest session of its type (`isLatest()`), the plan keeps every exercise, takes today's groups, and gains any new exercise right after the one done before it. Older days never change the plan.
  - **Reopening a saved workout** (the latest of its type) also shows the rest of the plan as not-started rows (`wExtra`, merged in plan order by `sheetEx()`). They aren't part of the workout until tapped (`takeExtra()` puts one in place and starts it), so a saved session never stores unstarted exercises. The sheet's group headings come from what's shown (`sheetGroups({type, exercises: shown})`), so their groups get headings too. Adding one by name via + Add takes it from `wExtra` too.
  - `weight`/`reps`/`sets` on an exercise mirror its best set and the count (`syncEx()`), so charts and summaries read them unchanged; `ensureSets()` converts old exercises. −/+ steps weight by 5 lb (2.5 kg). Exercises with "cable" in the name get an lb/kg toggle (converts sets, hints and the bump). A workout autosaves as a draft (`saved: false`). "Reorder or remove" (`wEdit`, closes the open exercise) shows group headings (`.ex-ghead`) and one row per exercise (`editRow()`): hold a row about 280 ms (or press its dots) to drag it, including past a heading into another group (`startDrag`/`placeDrag`/`endDrag`; headings shift like rows). Tapping a name renames it (`commitRename`/`renameAsk`/`renameExercise()`/`mergeSame()`). Remove has Undo.
- **Strength tickers (Progress tab):** per-exercise "stock ticker". Change is measured on estimated 1RM, `w × (1 + reps/30)` (Epley), so 45×12 → 50×7 reads as a small drop. Bodyweight exercises (weight 0) compare reps. An exercise lists under its home tab only (order from `m.types`: type → its position in that day's latest session), with all its sessions in one chart, "also on …" under its name for other day types it was done on, and the day type in its session rows. The open exercise is wrapped in `.tick-focus` (outline and soft tint, green unless its last change was down). The open chart has round grid lines, a line/dots/shading colored per stretch (green up or flat, red down), and one upbeat line (`strengthNote()`: gain since the first session, best yet, or the best to aim for) tagged "est. 1RM".
- **Goals layout:** an overall bar, then goals grouped by `groupOf(g)` (keyword guess, or `g.group` set in Edit) into Strength / Cardio / Body, one collapsed row per goal (`openGoal` expands one ladder at a time).
- **Goals:** ladders the owner wrote. Steps are stored easiest → hardest and shown hardest at the top in the open ladder. Each collapsed row shows a strip of three (`goalStrip()`): the step before (grey), the step you're on (the last one ticked), and the next step (the first not done), which is a button that ticks it (`goal-tick`) without opening the ladder. Five slots are drawn so `slideStrip()` can slide them one place left (or right, for the toast's Undo) before the redraw. A tap within 300 ms of a page scroll is ignored (`lastScroll`), so stopping a fling never ticks a step. No steps done shows "Start"; all done shows "All done".
- **Coach (Today, under the streak):** installed app on phones with Gemini Nano (AICore) only; hidden elsewhere. `coachCheck()` asks `AndroidBridge.aiStatus()` (answers via `window.__aiStatus`: available / downloadable → "Set up coach" downloads it / downloading / unavailable). When it's available, the app calls the model's `warmup()` once so the first words come quickly. The app does the analysis and the model words it.
  - **Facts:** `buildFacts()` writes plain sentences: challenge day and aim; each daily task's last-7-day count, today's tasks still to do, and the streak against the best; calories, protein, sleep and steps as the week's average against the goal, with how far off it is (units and %, `Math.floor` so 219 of 220 g reads 99%), each against the week before. Close counts: within 2% / 50 kcal of the calorie range, max(5 g, 3%) of protein, 15 min of sleep, or 5% of steps is "on target", so it's a win, never a fix. Then a line of what's on target and what has room to grow; today so far ("the day isn't over"); training this week vs last and days since each day type; strength trend, biggest gains, new bests this week, and lifts stalled over their last 3 sessions; weight since day 1 and its trend over the last 3 weeks (least squares, at least 4 weigh-ins over 12+ days). Losing fat has a pace goal: 1.5–3 lb a week from 200 lb up, scaled to 0.75–1.5% of body weight below that. A "Pace check" line says inside it (sweet spot, near the slow end with room to lose a little more, or near the fast end; the top win), slower than it (room to lose more: calorie goal −150 or 2,000 more steps; a nudge), or faster (can cost muscle: eat 150–250 more; the top nudge). Building: +0.2 lb/week or more is the top win; stalled (slower than −0.25 / +0.1) while calories were on target on 60%+ of days, a "Plateau" line gives likely reasons (eaten − burned from `burnedOf()` close to even, within 200; or a deficit the scale hasn't shown yet; BMR down 30+ since day 1; or simply being lighter) and a course correction (calorie goal ±150, or 2,000 more steps), which is also the top nudge; resting HR; each goal ladder (steps done, current, next, days since the last step) and goal steps ticked this week, labelled as milestones the user set (a step's number isn't what they did); a goal whose name matches a logged exercise (`bestFor()`, word match ignoring plurals) also gets their best logged set, so "20 in one go" ticked doesn't read as 20 done when the best set was 25. The prompt says the same. The app's candidates (`wins`/`fixes`, each with a weight) go to `factPicks` rather than into the facts, so the facts only change when the numbers do. When a note is written, `choosePicks()` picks the lead at random among the top 4 wins and the nudge among the top 3 fixes, skipping whatever the last note led with or nudged (`topicKey()`, stored as `picks` with the saved note), except that a fix weighted 0.9+ (pace, plateau) is always the nudge. The prompt says to open with the lead, then the nudge if it fits, then anything else.
  - **Prompt:** `coachWrite()` gives the coach its values (lead with what's going well; close counts and is never a miss; progress over perfection; be specific; one idea, never a lecture; a plateau is said plainly but kindly, with the reason and the fix the facts give), the facts, and the lead and nudge `choosePicks()` chose, then room to say whatever else matters. It asks for 2–4 sentences under 80 words that make you feel good and keen, using only these numbers. `aiGenerate` (temperature 0.5, top-K 24, 220 output tokens) streams the reply as it's written to `window.__aiChunk(textSoFar)` and ends with `window.__aiResult`. Requests to the model queue one at a time (`aiAsk(prompt, cb, onText)`).
  - **First hello:** until `hundred-days-hard.coachIntro` (localStorage, per phone) has `started`, `coachWrite()` writes the hello instead (`coachIntroWrite()`): Gemini Nano introduces itself in its own words, in a vibe picked at random from `VIBES`, with the user's day, aim and tasks, says it runs on the phone's own processor so the numbers never leave it, and asks if they're ready (`INTRO_FALLBACK` if it fails). The card shows it with **I'm ready** (`coach-start`), which marks it started and writes the first note with `coachFirst` (the prompt asks for a short natural lead-in like "Well then, let's have a look at your charts.").
  - **Card:** `coachHTML()` draws a gradient edge and glow, an avatar, "Today, 1:41 PM" / "Writing…" / "Nice to meet you", and the note with its numbers in bold (`coachRich()`: split on numbers, then escape). While writing, until the first words arrive, it shows `coachLoader()`: a barbell with three red 45s a side that slide on from the ends (innermost first, `bb-0`–`bb-2` keyframes), sit, then slide off (outermost first), with a caption about what it's reading (`CAPTIONS[kind]`, swapped every 1.2 s by `startCaptions()` for every `.load-cap` on screen, by its `data-kind`; it stops once neither coach is writing). Words then ink in character by character (`typer = makeTyper("coach-body", …)`, with `.to()`, `.html()`, `.reset()`: at least 55 characters a second, faster when the model is ahead; the newest 6 characters fade in), surviving redraws (`typer.html()`). The card body fades in (`.coach-body.enter`) only when what it shows changes (`coachShown`). The reply is cleaned (`coachClean()`: markdown, labels, and em dashes, which become commas; the prompts also forbid them) and stored in localStorage (`hundred-days-hard.coach`, not in backups). A new note is written on a new day, when the numbers change (at most every 2 hours; the age is checked before the facts are worked out, since that's the slow part), or from the menu. A note it writes on its own first runs a full `stats`-scope sync (unless one ran in the last 15 minutes) and waits for it (`coachAwait`, at most 20 s; the card shows the barbell with "Getting your latest numbers…"), then `__healthResult` calls `coachWrite()` again; a failed sync just writes with what's there (`coachSyncTried` stops a retry loop). Write a new note from the menu writes straight away.
  - **Menu and settings:** the ⋯ menu (`coach-menu`, a popover kept in the DOM and toggled by class; closes on a tap outside or Back) has Write a new note, Minimize / Show in full, and Turn off coach. `settings.coach` is unset (on), "min" (one line, tap to open; `.coach-body { min-width: 0 }` keeps that line from widening the page) or "off" (hidden, nothing generated). Settings → Coach has On / Minimized / Off. Tapping the note minimizes it; tapping the minimized line opens it.
- **App icon and launch screen:** a red bumper plate with two grip handles, a slim steel hub and "100", tilted 40° clockwise (`TILT` in `tools/make_icon.py`). Edit `tools/make_icon.py` and rerun it to change the icon. Android can't change a normal app's launcher icon by date, so the icon always says 100. The launch screen (Android 12+) shows the plate on the page color until the page has loaded (at most 2 s). The iPhone web app icons in `web/icons/` are rendered from the same drawing.
- **Feels like an app:** `buzz(kind)` gives haptics through `AndroidBridge.haptic()` (the WebView's `performHapticFeedback`: no vibration permission; "tick", "confirm", "start", "end"), or `navigator.vibrate` elsewhere. `TAP_BUZZ` lists the actions that tick on tap (tabs, Settings, Progress, every workout-logging control). "confirm" is used for task and goal ticks, adding an exercise, saving a workout, a food bar reaching its goal mid count-up, drags, and pull-to-refresh. Tabs slide in with `slideIn(dir)` (Web Animations, 200 ms). Pull down at the top of Today (APK, Samsung Health connected) to run `healthSync()` (`ptr` touch handlers and `#ptr` indicator: arrow, turns green past 64 px, spins until `__healthResult` or 8 s). Text selection, long-press menus (`contextmenu`) and pinch-zoom are off except in inputs. Toasts are `width: max-content`, so short ones stay on one line.
- **Home-screen shortcuts:** `android/res/xml/shortcuts.xml` (Push/Pull/Legs, icons `sc_*.xml` in plate colors) opens `hundreddayshard://log/<type>`. `MainActivity` (singleTask) keeps it until the page asks (`takeShortcut()` at startup), or calls `window.__shortcut(type)` if the page is already running. That starts the workout, or opens today's if there is one.
- **Backup:** APK writes `Download/100 Days Hard/100-days-hard-backup.json` about 1.5 s after any change (skipped while the app has no data, so a fresh install can't overwrite a good backup). "Send a copy" opens the share sheet. Restore merges by `updatedAt` per document, newest wins. The web version saves to the account automatically and can save/restore the same file.

## Shipping a change

1. Edit `app.html` (and `android/` if native code changes).
2. Regenerate test pages with `python3 tools/wrap_page.py android/assets/index.html` and `web/build.sh` (serve `dist/web` with `python3 -m http.server`). Test in Chromium with Playwright at 412×915 (the owner has a Samsung S25 Ultra). To exercise APK-only paths, inject a fake `window.AndroidBridge` with an init script (see the methods in `MainActivity.Bridge`). Check for page errors, and take screenshots for anything visual (keep test scripts and screenshots in the session's scratchpad, not the repo).
3. Optionally `TEST=1 android/build.sh` to check it compiles (the first Gradle run downloads a lot; later runs are quick). Don't hand that APK to the owner; it won't install over theirs.
4. Bump `android/VERSION`, add the changelog section, commit, push to `main`. That triggers the "Build APK" workflow, which publishes the signed APK to the repo's Releases page. The owner installs it over the old one.
   - Claude sessions can push `main`, but can't push or delete tags, view Actions runs, create releases, or set secrets (the session's GitHub proxy blocks those). Reading releases does work, so check that a build landed with `gh api repos/Xxytham/hundred-days-hard/releases`. Download the asset with `gh api -H "Accept: application/octet-stream" repos/Xxytham/hundred-days-hard/releases/assets/<id>`, and confirm its signer SHA-256 is `9851d428…fb26b` with `apksigner verify --print-certs`. If a build is missing, ask the owner to check the **Actions** tab, or the **Releases** page at https://github.com/Xxytham/hundred-days-hard/releases, and to use **Run workflow** on "Build APK" if a build needs re-running.
5. Republish the web version: `Artifact` read of the URL first, then publish `app.html` with `url` set to it. Keep capabilities `{db: {}, user: {}, downloads: true}`.

## Design

**Motion.** Every animation follows the same rules, so none of them draw attention to themselves:
- Only in answer to a tap, never looping or idle.
- Short: about 200 ms (`--t`), easing out with `--ease`; leaving is quicker (about 120 ms) than arriving.
- Small: moves of about 10 px or one slot, scale no lower than 0.95.
- Cheap: animate `transform` and `opacity` only (a short color fade on a small element is fine). Never animate width, height or position, which force layout every frame. For bars, scale them with `scaleX`.
- Keep animating elements in the DOM and change a class, rather than rebuilding them; new elements skip their transition.
- Everything is switched off under `prefers-reduced-motion`.
One deliberate exception: the food bars count up over about 700 ms, driven by requestAnimationFrame (number, `clip-path` width and color together), because the owner wants to watch them fill.
The pull-to-refresh spinner turns only while Samsung Health is being checked (at most 8 s), and the coach's barbell loader runs only until its first words arrive (usually a second or two), after which its words ink in as they're written.
Logging a set moves straight on (no animation). Current uses: the + menu (fade and rise, staggered 30 ms, + turns to ×), the coach's ⋯ menu (fade and small drop), the goal strip slide, the food box fill, the sheet rising, rows sliding aside while you drag an exercise, and the Progress focus fading in.

Bumper-plate palette (red 25 kg, blue 20 kg, yellow 15 kg, green 10 kg) over cool steel neutrals, with light and dark themes as CSS tokens on `:root`. Saira Condensed for display, Figtree for body. The owner likes the look, so keep new UI in the same system.
